# Minecraft 26.4 release-day runbook

Family Tree already builds a Fabric target named `26.4-snapshot-6`. On release day, move that target to the release, repeat the in-game checks, and publish. Budget about two hours: 20 minutes to port, 30 for NeoForge if it has a build, 45 for in-game checks, and 25 to publish.

## 1. Confirm the release

```sh
python scripts/check_mc_release.py 26.4
```

Exit code 0 means Mojang released 26.4 and Fabric API has a build for it. 1 means the release is out but Fabric API isn't, and 2 means the release isn't out. The output also names the NeoForge build and the newest Jade, WTHIT, Mod Menu, JourneyMap, and Xaero's Minimap builds for 26.4. `--json` prints the same report for a scheduled task.

## 2. Move the Fabric target to 26.4

Branch from an up-to-date main, then rename the target in the build files:

```sh
git switch -c feat/mc-26.4-release origin/main
git grep -l '26\.4-snapshot-6' -- '*.gradle' '*.yml' '*.py' | xargs sed -i 's/26\.4-snapshot-6/26.4/g'
```

That touches `settings.gradle`, `build.gradle`, `stonecutter.gradle`, `.github/workflows/build.yml`, and `scripts/release_manifest.py`. Then edit by hand:

- `build.gradle`: set the `'26.4'` Fabric API entry to the version from step 1. Read the loader floor with `unzip -p fabric-api-<version>.jar fabric.mod.json`. Keep `0.20.1` in the loader map unless Fabric API asks for newer, and test with the version you declare. In the `'26.4'` integration entry, use Mod Menu's 26.4 build. Switch Jade from `26.3.5+fabric` to its 26.4 build if one exists. Add `journeymap` and `xaero` entries when they have builds.
- `scripts/release_manifest.py`: empty `SNAPSHOTS` (`SNAPSHOTS = set()`), so the 26.4 jar enters the release as a normal file.
- `CLAUDE.md`, `README.md`, and `docs/testing.md`: replace each mention of the snapshot target with 26.4. `git grep -n 26.4-snapshot` finds them.

Build and fix what changed after snapshot-6:

```sh
./gradlew :26.4:build --no-parallel
```

Write 26.4-only code behind `//? if >26.3 {` conditionals. `>=26.4` would skip snapshots, pre-releases, and release candidates, because Stonecutter sorts `26.4-snapshot-6` before `26.4`. The existing `>26.3` blocks in `FamilyTreeScreen`, `FamilyTreeSettingsScreen`, and `PetFaceRenderer` cover the render signature, widget visibility, and portrait changes that arrived by snapshot-6. If Loom 1.16.3 can't set up 26.4, raise `loom_version` and `loomx.loom_version` in `gradle.properties` and run `buildAll`, because Loom is shared by every Fabric target.

If you changed shared source or Stonecutter rules, generate every target before and after and diff `versions/<v>/build/generated`. Only 26.4 should change.

## 3. NeoForge, if step 1 found a build

- `neoforge/build.gradle`: add `'26.4': '<version>'` to `neoVersions`, `'26.4': '26.5'` to `neoUpper`, and a `'26.4'` integration entry. Jade, JourneyMap, and Xaero's Minimap may need their 26.3 versions or none.
- `stonecutter.gradle`: append `'26.4'` to `neoForgeTargets`, and make `buildForge1_20_1` run after `buildNeoForge26_4`.
- `scripts/release_manifest.py`: add `'26.4'` to the NeoForge `TARGETS` and to `NEOFORGE`. If the NeoForge version ends in `-beta`, extend the `release_type` rule that marks NeoForge 26.3 as beta.
- `.github/workflows/build.yml`: add `{loader: neoforge, minecraft: '26.4'}`.
- `./gradlew -p neoforge build -Pminecraft=26.4`. The adapters in `neoforge/src/main/java` use `RegisterPayloadHandlersEvent`, `RegisterClientPayloadHandlersEvent`, `ClientPacketDistributor`, `PacketDistributor`, `RegisterKeyMappingsEvent`, `ClientTickEvent`, `IConfigScreenFactory`, and the entity join, leave, death, and interact events. Check those first if it fails to compile.

## 4. In-game checks

Use Xvfb, `-Xmx2G` at most per game, and disposable directories under `build/`. [Testing](../testing.md) covers the setup, and its Minecraft 26.4 snapshot section lists what ran on the snapshot.

1. Run `./gradlew :26.3:runSmoke -Psmoke` on a fresh world, copy `build/smoke-26.3/smoke` into `build/smoke-26.4/`, and run `./gradlew :26.4:runSmoke -Psmoke -PsmokeHistory=<records in the 26.3 world>`.
2. Generate a flat world: run `java -Xmx2G -jar ~/.gradle/caches/fabric-loom/26.4/minecraft-server.jar --nogui` in an empty directory with `eula=true`, `level-name=Family Tree demo`, and `level-type=minecraft\:flat`, then `stop` it. Copy the world to `build/demo-26.4/saves/Family Tree demo`, and run the demo, then `-Panimals`, `-Phorses`, `-Pgameplay`, `-Pplanner`, `-Prelatives`, and `-Pintegrations=modmenu` plus any map mod with a 26.4 build. Reset the world between runs. Look at every screenshot and both exports.
3. Run the release jar on a Fabric dedicated server and join with a portablemc client. Tame two wolves with bones, feed them beef, and let them breed. Tame two horses by riding them, then breed them with golden carrots. Open the browser with **H**, click a row to open a tree, click and drag in the tree, rename, export, and open settings, help, and the feedback form without pressing Send. Restart the server and client and check the history.
4. Join the same server with an unmodded 26.4 client. Run `/familytree`, open a family, try shift-click, number keys, and `Q`, and compare `data get entity <player> Inventory` before and after.
5. If NeoForge is in, run its smoke and demo with `-Pminecraft=26.4`.

## 5. Release and publish

1. Family Tree 1.4.0 shipped before 26.4, so the 26.4 notes go into the next version's file, such as `docs/releases/1.4.1.md`. Start from this draft. Update the NeoForge cell, the Loader floor, and the integrations line from step 1, and list only what step 4 checked:

   ```markdown
   ## Minecraft 26.4

   Family Tree runs on Minecraft 26.4 with Fabric. It needs Fabric API for 26.4, Fabric Loader 0.20.1 or newer, and Java 25.

   | Minecraft | Fabric | NeoForge | Forge | Java |
   | --- | --- | --- | --- | --- |
   | 26.4 | Fabric API for 26.4 | No build yet | No build | 25 or newer |

   - History carries over. A 26.3 world opened in 26.4 keeps every pet, parent, death, custom name, and horse stat, because 26.4 reads the same `familytree.dat` file.
   - Every feature of the 26.3 build works on 26.4: the browser, trees, the breeding planner, the relatives key, model portraits, PNG export, horse stats, the chest menus for players without the mod, and Mod Menu's Configure button.
   - Jade, JourneyMap, and Xaero's Minimap had no 26.4 builds when this file was built, so their tooltips and waypoints on 26.4 are untested.
   - NeoForge has not published a 26.4 build yet. A NeoForge file follows once it does.
   ```

   Add the same row to the table in `modrinth_description.md`, add `| 26.4 | Fabric | 25 or newer | Fabric API for 26.4 |` to the README install table, replace the README's sentence about 26.4 snapshots, and run `python scripts/curseforge_description.py`.
2. Open a PR and squash-merge it once every CI job passes.
3. Pick the version. If main is ready to release, bump `mod_version`, commit, run `./gradlew buildAll --no-parallel`, then `python scripts/release_manifest.py`. `publish_modrinth.py` skips a version already on Modrinth only when its file hash matches and stops otherwise, so rebuilt jars need a new version number. `release_manifest.py` refuses to write into a `build/releases/<version>/` folder whose manifest records another commit.
4. To ship only the 26.4 file under a new patch version, write `docs/releases/<version>.md` first, because both publishers use it as the changelog. Build and generate the manifest as above, then filter it:

   ```sh
   python - build/releases/<version>/manifest.json <<'EOF'
   import json, sys
   path = sys.argv[1]
   manifest = json.load(open(path))
   manifest['files'] = [f for f in manifest['files'] if f['minecraft'] == '26.4']
   json.dump(manifest, open(path.replace('manifest.json', 'manifest-26.4.json'), 'w'), indent=2)
   EOF
   ```

5. Publish with the publish scripts, then tag:

   ```sh
   python scripts/publish_modrinth.py --manifest build/releases/<version>/manifest.json
   python scripts/publish_curseforge.py --manifest build/releases/<version>/manifest.json --first-upload
   git tag v<version> && git push origin v<version>
   ```

   Use `manifest-26.4.json` instead for a 26.4-only release. CurseForge's upload token can't list a project's files, so `publish_curseforge.py` knows only the uploads recorded in `curseforge-published.json` next to the manifest. It refuses to start without that file unless you pass `--first-upload`, so check the CurseForge Files page before you pass it, and drop the flag when you retry. It also stops if CurseForge doesn't list a game version named exactly `26.4` yet. Retry later in that case.
6. Run `python scripts/check_mc_release.py 26.4` again in a few days. When Jade, JourneyMap, or Xaero's Minimap publish 26.4 builds, run the integration scene with them and update the notes.

## A snapshot alpha before release day

`python scripts/release_manifest.py --snapshots` also verifies and copies the snapshot jar, marked `alpha`, with game version `26.4-snapshot-6`. Publish it to Modrinth from a manifest filtered to that file as in step 5.4, with `f['minecraft'] == '26.4-snapshot-6'`. Upload it to CurseForge only if CurseForge lists a game version with that exact name. The jar declares `minecraft =26.4-alpha.6`, so it refuses to load on any other snapshot, and each new snapshot needs a new build.
