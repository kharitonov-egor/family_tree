# Family Tree audit and plan for 10,000 downloads

Audit date: September 29, 2026, New York time. Public data was fetched around September 30 at 00:50 UTC. Counts are a snapshot, not a live dashboard.

Family Tree has a clear reason to exist. Minecraft forgets a pet's parents, and players care about the animals they have kept for years. The searchable history, death records, and image export make that history visible. I would build the next release and its promotion around that promise.

The immediate priorities are release reliability, support for the current Minecraft release, and a short demonstration that makes someone want their own tree. Another large feature list is less likely to help than those changes.

## Scope and evidence

I reviewed the current working tree, including the uncommitted 1.0.1 work, shared Java code, both loader integrations, persistence, permissions, networking, tree navigation, export, tests, build scripts, documentation, and release metadata. I inspected the live Modrinth description and versions in the browser, fetched its public API data, checked the public GitHub repository, inspected the screenshots and export, and compared adjacent pet mods.

All four local 1.0.1 release jars matched the SHA-512 hashes published on Modrinth before the fresh verification runs. The code findings therefore concern the shipped build, not just an unpublished proposal. Public GitHub main still points to commit `60569ea`, whose version is 0.3.3. Much of the shipped 1.0.1 source is uncommitted in this checkout.

I added this report and an isolated probe under the ignored `build/audit-2026-09-29/` directory. I did not edit production code, publish releases, or contact anyone.

| Check | Result |
| --- | --- |

| Fresh JUnit runs | 28 tests passed on each target, 112 executions in total. These are the same shared tests across four targets. |
| Fresh dedicated-server smoke runs | Fabric 1.21.1, 26.1.1, 26.2, and NeoForge 26.2 passed in their existing disposable test worlds. |

The smoke runner calls the breeding method and death handler directly. It verifies useful behavior, but does not prove every real death event, tame event, canceled event, or multiplayer permission transition. Its retained-history count is not an immutable previous-release migration fixture.

## What already works

- The mod solves a specific omission in vanilla Minecraft. Parentage and deceased pets give it a stronger identity than a general pet list.
- Existing pets enter the tracker as their chunks load. The welcome message and Find existing pets button already help the first session.
- Edit and locate actions check ownership on the server. Public snapshots remove foreign pet coordinates, and tests verify that behavior.
- Manual links reject ancestry loops and recheck permissions at confirmation time.
- Tree names preserve the animal's name tag. That is a useful distinction and the page explains it.
- PNG export already includes a Modrinth URL and excludes explicit owner and location fields. It is the best existing way for a player to introduce the mod to someone else. User-entered pet names can still contain personal information.
- The page has a real screen recording, a readable export, installation instructions, and an honest explanation of unknown older parentage. Keep those assets.
- Shared code and loader adapters reduce duplicate implementation work. Do not rewrite the project just to make the architecture look tidier.

## Technical findings, ranked

P1 means fix before broad promotion to servers or modpack authors. P2 means schedule for the next maintenance release. P3 means address when demand or measurements justify it. Reproduced findings and code-inspection risks are identified separately.

### P1. The snapshot count limit does not enforce the packet byte limit

Evidence: [FamilyTreePackets.java](../src/main/java/com/egakh/familytree/network/FamilyTreePackets.java), lines 53 and 62, and [FamilyTreeSnapshotPayload.java](../src/main/java/com/egakh/familytree/network/payloads/FamilyTreeSnapshotPayload.java), line 23.

The server allows 8,192 records in one snapshot. The probe encoded that many populated wolf records with names, parent IDs, owners, variants, and last-seen data into 1,694,642 bytes. Minecraft 26.2's clientbound custom-payload limit is 1,048,576 bytes. The measurement excludes the payload identifier, so it already exceeds the budget before packet overhead.

This reproduces an encoding-size failure, not an observed disconnect in a live multiplayer session. A sufficiently large allowed snapshot cannot fit the native packet budget. Compression should not be treated as a fix for a decoded-payload size limit.

Send byte-bounded pages or separate a lightweight browser index from requested family data. Include a request ID and completion information so the client assembles a consistent result. Set a byte budget below the native limit and test populated records, long names, death causes, and Unicode. Preserve permissions on every page.

### P1. Expensive requests are not fully rate limited

Evidence: [FamilyTreePackets.java](../src/main/java/com/egakh/familytree/network/FamilyTreePackets.java), lines 27, 31, and 42, and [FamilyTreeCommand.java](../src/main/java/com/egakh/familytree/command/FamilyTreeCommand.java), line 238.

Open requests always filter and serialize a snapshot. Discovery limits the scan to once every two seconds per player, but still sends a full snapshot for every request during the cooldown. Rename requests have no mod-level rate limit. The scan command bypasses the discovery cooldown and iterates loaded entities in every dimension on the server thread.

This is a confirmed code path, not a measured server outage. A modified client or command automation can make the server do much more work than the normal UI permits.

Share throttling between UI and commands. Return before both scan and snapshot work when a request exceeds its limit. Add a server-wide scan budget as well as a per-player budget. Cache snapshots or indexes by state revision where useful. Verify that a rejected burst does not repeatedly scan, serialize, or dirty the save.

### P1. The release cannot be rebuilt from its advertised public source

Evidence: public GitHub main is `60569ea`, version 0.3.3. Modrinth ships 1.0.1. GitHub's latest release and tag are 0.3.1. No tracked `.github` workflow exists.

The local jars match Modrinth, which is good evidence that this checkout contains the release. But someone following View source cannot obtain a committed 1.0.1 source tree, reproduce it, or send a fix against that exact release.

Commit the reviewed release source, tag it, and attach the same tested artifacts to a release. Add a four-target build and test workflow with a release manifest containing game version, loader, mod version, commit, dependency IDs, and hashes. Pin the declared Loom snapshot dependencies to a tested fixed version. Publishing should consume the verified artifacts rather than rebuild them separately.

### P1. MIT licensing is declared without the license text

Evidence: README links to `LICENSE`; both loader metadata files and Modrinth declare MIT. No LICENSE file exists in the checkout or public repository. The inspected release jar contains no license text. GitHub reports no detected license.

Add the MIT license with the correct copyright holder and year. Include it in both loader jars. Check the Fabric jar task's path, since Stonecutter runs version subprojects, and add equivalent packaging for NeoForge. This is a small fix that removes avoidable doubt for contributors and pack authors.

### P2. More than 8,192 visible records silently disappear from the response

Evidence: [FamilyTreePackets.java](../src/main/java/com/egakh/familytree/network/FamilyTreePackets.java), line 62.

The limit takes the first records from a ConcurrentHashMap collection without a stable sort, total count, or truncation flag. Saved records remain, but the UI can omit pets and parent links without explanation. Reopening can produce an incomplete tree that looks like lost history.

Pagination should solve this alongside the packet-size finding. Until then, report the total and omitted count explicitly and use deterministic selection. Do not silently export an incomplete family as though it were complete.

### P2. Name-based edits can change an arbitrary pet

Evidence: [FamilyTreeCommand.java](../src/main/java/com/egakh/familytree/command/FamilyTreeCommand.java), line 374. Pair, unpair, setage, and setbirth use a first matching record. Info also selects the first match.

Two manageable pets named Rover are enough to trigger this. The map's iteration order decides which one gets edited. The docs tell players to assign unique tree names, but the command still accepts ambiguous input. Original-name aliases also remain valid after a tree rename.

Reject multiple matches and show choices containing species and a short ID. Accept an exact UUID or offer a selection UI. Test duplicate original names and a tree name that matches another pet's original name.

### P2. Generation calculation can overflow the Java stack

Evidence: [Genealogy.java](../src/main/java/com/egakh/familytree/util/Genealogy.java), lines 41 and 53. The view computes generations for the whole snapshot before laying out the selected family.

An 8,192-record ancestry chain caused StackOverflowError with a 1 MiB stack in the probe. Normal shallow families are unlikely to hit this. Imported, manually linked, or very old graphs can. The existing deep ancestry test covers iterative cycle validation, not recursive generation calculation.

Use iterative generation calculation with explicit handling for old cycles and missing parents. Test deep graphs in both generation entry points. A focused tree's six-generation display limit does not protect this calculation because the full snapshot is processed first.

### P2. Save recovery silently drops malformed records and ignores future versions

Evidence: [FamilyTreeState.java](../src/main/java/com/egakh/familytree/data/FamilyTreeState.java), lines 94 and 100.

The tolerant list correctly keeps good records when one record is corrupt. However, it discards decode errors without logging them. The codec also ignores the parsed `data_version`. The probe supplied version 999 with one valid and one malformed record. Loading succeeded with one record, and re-encoding omitted the version as the current default 1.

Keep tolerant recovery. Add a skipped-record count, diagnostics, and a preserved copy or quarantine for rejected data. Warn the administrator before an ordinary save replaces the original file. Refuse to rewrite an unsupported future format without an explicit recovery path. Add fixtures exported by actual older releases, not just current-code round trips.

### P2. Legacy import can restore intentionally deleted history

Evidence: [FamilyTreeState.java](../src/main/java/com/egakh/familytree/data/FamilyTreeState.java), lines 140 and 158.

This is a conditional code-inspection finding. If a readable legacy file remains at `data/familytree.dat`, emptying the modern store triggers the legacy import again on the next state lookup. Pruning every record can therefore restore the old history. The fallback also expects `records` at the NBT root, uses a strict list, and suppresses I/O errors. It needs fixtures for both raw legacy files and normal SavedData wrappers.

Run migration once per store initialization, record its completion, preserve the old file as a backup, and log failure details. Test pruning to empty after migration and restarting. Do not infer that every empty modern store needs recovery from the old file.

### P2. Compatibility metadata and testing do not cover the same versions

Evidence: [build.gradle](../build.gradle), line 48, and the public version listings.

The 1.21.1 Fabric jar declares `~1.21.1`. The Fabric version-predicate probe confirmed that this accepts Minecraft 1.21.11, even though the source transformations and testing target 1.21.1. This leaves unsupported versions eligible to try loading the jar. It does not prove that every accepted patch fails.

In the other direction, the 26.1 jar accepts the 26.1 series internally, but the 1.0.1 Modrinth release lists only 26.1.1. A player filtering for 26.1.2 sees an older beta rather than a tested current release. Test the intended patches, list those that pass, and narrow the jar dependency predicate to the versions actually supported. Test the lowest Fabric Loader version you claim too, or raise it to a verified minimum.

### P2. Old Modrinth releases still make installation harder

Evidence: public version IDs `9j4QmEV4`, `tJWEkJby`, and `jKecFBLl`.

Version 0.3.2 advertises 26.1.1 and 26.2 with two different jars but only one primary file. Tools choosing the primary file cannot use the version's game tags to distinguish those jars. Versions 0.3.0, 0.3.1, and 0.3.2 have no required Fabric API dependency in Modrinth metadata. Current 1.0 releases correctly declare Fabric API and use separate entries.

Correct old dependency metadata, clarify or separate the old compatibility entries, and point users toward verified current versions. Preserve old files for users who need them. The broad 26.1.x compatibility badge currently includes versions available only through those older releases.

### P3. Several smaller gaps affect long-term use

- Individual trees stop at six generations in each direction. Show an explicit boundary and a way to request more, especially before export. The current phrase "whole visible tree" is defensible but easy to read as all recorded descendants.
- A screen snapshot does not automatically refresh when another pet is born, renamed by someone else, or dies. Add a Refresh action or inexpensive revision notifications. A staged animation should not imply that every open screen already updates live.
- Manual pairing requires all three pets to have the same species. That prevents restoring a known horse and donkey family for a mule. Make any hybrid exception explicit and tested.
- Existing deceased records never become alive in `ensureRecord`. A revival mod preserving the UUID would leave the pet recorded as dead. Test Respawnable Pets before claiming compatibility and decide how repeated deaths belong in the history.
- Prune deletes records immediately. Add a preview count and a backup or confirmation to protect the history the mod exists to preserve. Deleted parents leave descendant references pointing to missing records.
- Browser rows and tree cards are custom mouse targets rather than normal focusable widgets. Add keyboard selection, narrator descriptions, and visible filter selection. Test compact windows and larger GUI scales with long names.
- Only `en_us` is present. Some age, species, and command output bypasses translation keys. Move those strings into keys before inviting translators.
- Export success reports a folder, not the actual file or an Open folder action. A small improvement here makes sharing easier. Portrait extraction assumes vanilla texture layouts, so test resource packs that change pet models.
- Preview entity caches retain a level until another level is rendered. Clear them on disconnect. Linking sessions also need cleanup on logout or server stop, rather than expiration checked only when reused.

## Product direction

The primary audience is a survival player who has named pets and keeps one world for months. The next audience is a cozy or vanilla-plus modpack author who wants a small addition with little gameplay disruption. Horse breeders are a useful third audience, but their needs include hybrid lineage and possibly breeding statistics.

The clearest promise is "Keep your pets' history, including the ones you lost." Lead with a specific wolf family, show a descendant, then show the exported tree. Finding a missing pet is a second reason to install. Explain last-known locations beside that promise so it does not sound like an unloaded-entity radar.

The first-session problem is that players install the mod after their existing pets already have unknown parents. They can see a list immediately, but may not see the family tree that persuaded them to install. Improve that moment with a clearly marked read-only example, an in-screen explanation of discovering pets, and a guided way to add a family they know. The current welcome message and scan button are a good start.

The linking stick takes an anvil, a special name, three clicks, and chat confirmation. Keep it for players who like in-world tools, but consider a simple owner-only "Add parents" action in the tree. Show the selected pets and validate before confirmation. Do not make players guess the command syntax to recover a known family.

I would defer cloud accounts, public profile hosting, a genetics simulation, paid promotion, and a large Discord community. Each adds work without first proving that players install and share this mod. Keep support in GitHub issues until the volume warrants another place.

## Modrinth page recommendations

The page already has the right basic ingredients. Do not replace its screenshots with mockups or remove its limitation notes.

1. Test a more specific title such as "Family Tree for Minecraft pets". A web search for the generic name also returns villager-family mods and a WorldBox mod. Put wolves, cats, pets, and family history in natural sentences, rather than adding a list of search keywords.
2. Move the singleplayer and multiplayer installation requirement above the first demo or directly below it. A client-only installation on someone else's unmodified server cannot provide the history tracking shown.
3. Use a crop of the exported three-generation wolf family as the first image, then the actual gameplay clip. The 1.98k-wide export is more legible at page width than an entire 1.6k-wide game screen. Keep a gameplay screenshot in the gallery to establish what the UI looks like.
4. Add a real 15 to 25 second gameplay clip. Show two named wolves, actual breeding, the new child's parents, a deceased ancestor, and export. The existing 1.55 MB WebP uses staged data and labels it honestly. It is useful, but does not prove the whole player interaction.
5. Add a short "Works with pets already in your world" sentence, immediately followed by the limitation that earlier parents cannot be recovered automatically.
6. Keep the main description focused on installation and outcomes. Move the long command table to the linked guide after the public repository contains the current documentation. Retain the linking-stick introduction and the safety details players need.
7. Label old gallery images as an archive and order current screenshots first. They are already marked as previous releases, so this is polish rather than a major defect.
8. Add the icon and contact links to Fabric metadata so the downloaded mod looks complete in a mod list. Preserve the existing public icon, which already communicates pets and family relationships.

Suggested opening copy, to review before publishing:

> Keep your first wolf in the family tree after it's gone.
>
> Family Tree records your Minecraft pets, their parents, and their descendants. Find a missing pet's last known location, keep deceased pets in the family, and export a tree as a PNG.
>
> In singleplayer, install the matching mod file and press H. On a server, install it on the server for tracking and on your client for the screens. Fabric builds also need Fabric API.
>
> Pets already in your world appear as you visit them. Their earlier parents are unknown, but you can add relationships you remember. New births record parentage while the mod is installed.

This is a candidate, not a claim that different wording will raise downloads. Track it as a dated experiment.

## A six-month plan

The milestones below are targets that expose a shortfall early. They are not predicted outcomes.

| Time | Work to finish | Download checkpoint |
| --- | --- | --- |
| Days 1 to 7 | P1 repairs, accurate metadata, public release source, current-version tests, two short clips, revised opening copy | Establish the daily baseline. |
| Days 8 to 30 | 26.3 release, first NeoForge 1.21.1 build if feasible, creator trials, pack trials, one clear survival story | 1,000 total |
| Days 31 to 60 | Repeat the content format that brought clicks and installs. Publish verified compatibility notes and resolve trial feedback. | 2,500 total |
| Days 61 to 90 | Turn the successful trial into pack inclusion or recurring player shares. Release onboarding improvements justified by feedback. | 4,500 total |
| Days 91 to 180 | Expand the distribution that works, maintain game updates, and add one requested integration or version at a time | 10,000 total |

The last phase needs about 61 downloads a day if day 90 reaches 4,500. If it misses that checkpoint, recompute the rate and change the deadline or distribution plan. Do not hide the shortfall behind a new feature announcement.

### Creator experiment

Prepare a small kit with a 20-second landscape clip, a vertical crop, two readable images, the exact supported pairs, installation instructions, known limitations, and the project link. Use real game footage. An optional example world must match its advertised Minecraft version and keep staged data clearly labeled.

Select ten creators who have recently covered small Minecraft utility mods, pets, or long-running survival worlds. Favor a close match over a large subscriber count. Personalize each invitation around a specific recent video. Ask for a trial, not a promised endorsement. Do not pay for broad exposure before measuring whether the demonstration leads to installs.

A possible video opening is "This is the family of the first wolf I tamed in this world." Show the ancestor, its children, and the exported image before explaining the controls. A second format can show finding a missing pet, with the last-known-location limitation visible.

No outreach was sent as part of this audit.

### Modpack experiment

Choose ten active packs or small servers with pets, cozy survival, or vanilla-plus play on a supported pair. Supply the jar through the platform, required dependency details, the license, save paths, uninstall behavior, and compatibility results. Ask for a private trial in a disposable world before asking for inclusion.

Trial success means the maintainer can install it, open a pet tree, verify ownership restrictions, breed a child, restart without losing the family, and export an image. Record what failed. One maintained pack that keeps the mod can be more useful than many one-off announcements, but we do not yet have data to assign it a download value.

### Player-sharing experiment

Use the existing PNG export as the center of a weekly prompt such as "Show the oldest pet family in your world." Share your own actual survival family first. Keep the project URL in the image footer small and readable. Add Open folder or Open image after export so the player can find the file.

Post only in communities that permit the relevant kind of self-promotion. Choose one place for a first trial and read its current rules. Adapt the post to the community and respond to actual questions. Do not paste the same launch message across many communities.

### Measurement and decisions

Keep a dated log of total downloads, per-version downloads, followers, releases, published content, external link clicks if measured, pack trials, accepted inclusions, and bug reports. Fetch public counters once a day with a named User-Agent. Keep promotional links identifiable by campaign through a redirect you control if you need click counts. Do not assume Modrinth exposes public visitor counts or campaign-to-download attribution.

Use daily deltas and rolling seven-day totals. Label download spikes around releases separately because returning players may download again. Followers per download are not a conversion rate. Ask trial participants whether they still use the mod a week later. No in-game telemetry is needed for that first round.

| Observation | Next action |
| --- | --- |
| Content gets few views or project-link clicks | Change the first seconds and show the outcome sooner. Check whether the audience uses a supported version. |
| Many measured clicks, few downloads or many install questions | Check loader coverage, dependencies, client/server instructions, and page clarity. Attribution will still be approximate. |
| Downloads rise but trials stop using it | Improve first-session discovery and known-family linking. Ask what made the tree unhelpful. |
| Pack authors decline because of reliability | Finish the relevant technical fix and supply a repeatable test result. |
| One audience produces repeated use and shares | Make the next clip and one product improvement for that audience. |

For scale, 9,520 additional downloads would require 95,200 eligible page visits at an assumed 10 percent visit-to-download rate. At 5 percent it would take 190,400 visits, and at 20 percent it would take 47,600. These are arithmetic scenarios, not measured conversion rates. They show why 10,000 needs distribution as well as page copy.

At day 30, review the actual rate against the remaining target. If no format brings repeated clicks and installs, change the pitch and audience before adding more features. If pack trials fail, repair those failures before increasing outreach volume.
